# Local Quiz Game MVP — Implementation and Verification Skill Guide

## Purpose

This document defines the **implementation workflow**, **verification workflow**, and **quality gates** for building and maintaining the **Local LAN Quiz Game MVP**.

It is intended for:
- developers
- coding agents
- reviewers
- maintainers

This file should be treated as the **execution contract** for the project.  
When implementing or modifying the project, follow this document before writing code, during development, and before accepting changes.

---

## 1. Project Goal

Build a **LAN-only local quiz game** that runs on a host machine and is accessed by mobile clients through a browser.

Core product requirements:

- Runs on a **Windows host machine**
- Works on a **local Wi-Fi / hotspot network**
- Uses **Node.js + Express + Socket.IO**
- Frontend uses **HTML + CSS + JavaScript**
- Host and display may be **combined into one unified dashboard**
- Game can start with **1 to 4 teams**
- Teams join by **QR code**
- Each team uses **one mobile phone**
- Question answers are **shuffled once on the server**
- Score is **cumulative across questions**
- A **column/bar dashboard** shows cumulative team score after each question
- Clients only see their score **after the question ends**
- The system persists state and stores match history in JSON files

---

## 2. Non-Negotiable Product Rules

The following rules must not be violated unless the spec is intentionally changed.

### 2.1 Architecture Rules
- The **server is authoritative**
- Clients must never calculate official score on their own
- Question timer must be controlled by the server
- Answer shuffle order must be generated by the server and shared consistently
- Game state must have **one active global phase at a time**

### 2.2 Gameplay Rules
- Team count may be **1 to 4**
- The game must still progress through **all configured questions/stages** even if fewer than 4 teams joined
- Each team can submit **at most one final active answer per question**
- If the client submits before time ends, the client UI shows **Submitted / Waiting**
- A client sees score only **after reveal/end of question**
- Wrong answer or timeout = **0**
- Correct answer score formula:

```text
score = 40 + 60 * (time_left / total_time)
```

- Tie-break must be supported where needed
- Slide image is shown **after answer reveal / scoring**

### 2.3 Data Rules
- Questions are loaded from JSON
- Game state is saved to JSON
- Match history is saved to JSON
- Restore/recovery must not corrupt answer order, score, or phase

## 3. Recommended Development Order

Always implement in the order below unless there is a strong reason not to.

### Phase 1 — Project Skeleton
Implement:
- server bootstrap
- static routes
- socket server
- folder structure
- config loading
- question loading
- utility helpers

Verify:
- server starts
- host dashboard opens
- join page opens
- socket connection succeeds
- JSON config loads without crash

### Phase 2 — Team Join Flow
Implement:
- QR join URL generation
- join form
- team name validation
- icon selection
- waiting queue
- host accept/reject
- room lock behavior

Verify:
- team can join from mobile
- invalid names are rejected
- accepted teams appear in host dashboard
- more than allowed teams are not activated incorrectly
- game can still start with fewer than 4 accepted teams

### Phase 3 — Game State Machine
Implement:
- lobby
- question
- paused
- reveal
- scoreboard
- slide
- stage result
- tie-break
- finished

Verify:
- only one global state is active at a time
- transitions happen in valid order
- restore returns to a valid previous state
- UI updates correctly on all connected pages

### Phase 4 — Question Runtime
Implement:
- question start
- countdown timer
- pause/resume
- end question
- single server-side shuffled answer order
- answer submission
- answer lock

Verify:
- all clients see the same answer order
- timer stops on pause
- timer resumes correctly
- late answers are rejected
- duplicate answers do not overwrite score incorrectly

### Phase 5 — Scoring and Reveal
Implement:
- correct answer reveal
- score calculation
- cumulative scoring
- per-team result emission
- host dashboard cumulative column chart

Verify:
- score formula is correct
- wrong answer = 0
- no-answer = 0
- score is added only once
- client sees score only after question end
- host scoreboard matches persisted state

### Phase 6 — Stage Progression
Implement:
- stage completion
- adaptive progression for 1–4 teams
- optional elimination logic
- tie-break question support
- bonus/final stage behavior

Verify:
- game still proceeds with only 1 team
- game still proceeds with 2 or 3 teams
- progression does not break when fewer teams exist
- tie-break triggers only when needed
- bonus stage works as designed

### Phase 7 — Persistence and Recovery
Implement:
- autosave state
- history writer
- restore previous step
- safe file write strategy

Verify:
- crash/restart can restore valid state
- question order remains the same after restore
- shuffled answers remain the same after restore
- scores remain unchanged after restart
- history file is valid JSON

### Phase 8 — UI Polish
Implement:
- unified host/display dashboard layout
- responsive client layout
- scoreboard chart
- slide display
- clearer phase/status indicators

Verify:
- client UI is usable on mobile
- host dashboard is readable on laptop
- scoreboard columns represent cumulative score
- slide image changes do not break layout

## 4. Required File Responsibilities

These responsibilities should remain clear and separated.

### Server layer
Responsible for:
- game state
- timer
- score
- transitions
- persistence
- event broadcasting

Must not:
- depend on browser DOM
- trust client-side score/state

### Host dashboard
Responsible for:
- controlling flow
- showing QR
- accepting teams
- starting/pausing/ending question
- showing scoreboard/slide/game status

Must not:
- own official game logic
- calculate canonical score independently

### Client page
Responsible for:
- join UI
- answer UI
- waiting/submitted state
- showing personal result after reveal
- showing disabled/eliminated state

Must not:
- calculate official score
- decide whether a submission is valid
- infer hidden state before reveal

### Data files
Responsible for:
- storing durable configuration
- storing question bank
- storing game runtime state
- storing history

Must not:
- silently change schema without migration/update

## 6. Manual End-to-End Test Procedure

Use this exact sequence for manual QA.

### Test A — Minimal Team Count
Goal: verify the game works with fewer than 4 teams.

Steps:
1. Start server
2. Open host dashboard
3. Join with 1 team only
4. Accept the team
5. Start game
6. Run through all questions/stages

Pass criteria:
- game starts successfully
- no stage crashes
- team can answer
- score is shown after each question
- final state is reachable

### Test B — Standard Multi-Team Flow
Goal: verify normal match behavior.

Steps:
1. Start server
2. Join with 3 or 4 mobile clients
3. Accept teams
4. Start game
5. Submit mixed correct/wrong answers
6. Complete multiple questions
7. Move through reveal → scoreboard → slide → next question

Pass criteria:
- all clients stay synchronized
- cumulative score grows correctly
- host dashboard remains stable
- score chart reflects current totals

### Test C — Pause/Resume
Goal: verify authoritative timer behavior.

Steps:
1. Start a question
2. Wait until time is partially consumed
3. Pause from host
4. Confirm clients are locked
5. Resume
6. Submit answers

Pass criteria:
- timer stops during pause
- no client can submit while paused
- timer resumes from the same remaining time

### Test D — Recovery
Goal: verify restore behavior.

Steps:
1. Start a match
2. Reach question/reveal/scoreboard state
3. Save state automatically
4. Restart server or trigger restore
5. Re-open host/dashboard/client

Pass criteria:
- state reloads without corruption
- same scores are shown
- same phase is shown
- same question and shuffled answers remain intact

### Test E — Result Visibility Timing
Goal: verify client does not learn score early.

Steps:
1. Start a question
2. Client submits answer early
3. Observe client screen before timer ends
4. End/reveal question

Pass criteria:
- before reveal/end: only submitted/waiting state is shown
- after reveal/end: score is shown correctly

## 7. Bug Classification

Use these severities consistently.

### Critical
A bug is critical if it:
- corrupts score
- corrupts state
- breaks timer authority
- leaks result before reveal
- causes invalid phase transition
- prevents game progression

### Major
A bug is major if it:
- breaks join flow
- breaks pause/resume
- breaks scoreboard rendering
- breaks slide rendering
- breaks recovery for common states

### Minor
A bug is minor if it:
- affects style only
- causes non-blocking visual inconsistency
- causes small layout problems without gameplay impact

## 8. Definition of Done

A change is considered done only when all conditions below are true.

- [ ] implementation matches current spec
- [ ] no contradiction with server-authoritative design
- [ ] no contradiction with score visibility timing
- [ ] no contradiction with fewer-than-4 team support
- [ ] verification checklist passes
- [ ] manual end-to-end tests pass
- [ ] no console error blocks core flow
- [ ] persisted JSON remains valid
- [ ] changed behavior is documented if necessary

---

## 9. Common Mistakes to Avoid

Do not:
- hard-code logic that assumes exactly 4 teams are always present
- reveal client score before the question ends
- shuffle answers independently per client
- trust client timestamps as official scoring data
- allow multiple incompatible active phases
- overwrite persisted state without validation
- let UI-only code become the source of truth
- assume restore means "restart from beginning"

---

## 10. Suggested Implementation Notes for Agents

When modifying this project:

1. Read the current spec first
2. Identify which phase of the workflow your change belongs to
3. Change the smallest possible number of files
4. Verify both server logic and UI rendering
5. Update persistence logic if runtime state structure changes
6. Run startup + manual flow tests before declaring success

If a requested change affects:
- score timing
- game state transitions
- team progression
- persistence schema
- question lifecycle

then you must test the full affected flow, not just isolated code.

---

## 11. Final Rule

This project is a **stateful real-time multiplayer system**.  
Do not treat it like a static website.

Whenever in doubt:
- prefer server authority
- prefer explicit state transitions
- prefer deterministic behavior
- prefer testable flow over clever shortcuts
